# Release preparation: specialist subagents

**Status: prepared, not performed.** Nothing has been merged, version-bumped, tagged, published or deployed. Each of those is a separate action the owner authorizes.

## What the repository actually says about versions

There is **no written release policy** in this repository: no RELEASING document, no versioning section in the README, and no contributor guide. What the repository does encode:

| Source | What it fixes |
| --- | --- |
| `scripts/check-versions.sh` | `[workspace.package] version` in `Cargo.toml` and `frontend/package.json` must agree. On a tag build, the tag must be exactly `v<workspace version>`. |
| `.github/workflows/release.yml` | Triggers on `v*` tags and creates the release with `generate_release_notes: true`. It does **not** read `CHANGELOG.md`, so the changelog is documentation, not release input. |
| Commit `647758d` "chore: release v0.4.1" | The release commit changes exactly `Cargo.toml`, `Cargo.lock`, `frontend/package.json` and `frontend/package-lock.json`. |
| Tags | `v0.4.0` (2026-09-18) was the repository's extraction from Lightweight, a structural change. `v0.4.1` (2026-09-30) is the latest, published as Latest, and was a refactor. |
| `CHANGELOG.md` | Has no `[0.4.1]` section: v0.4.1's notes were generated by GitHub. Everything under `[Unreleased]` today postdates v0.4.1. |

The convention carried over from the Lightweight releases, a patch bump even when features are added, is recorded in the maintainer's notes, not in this repository.

## Recommendation: 0.4.2

- This stack (PR #30, then #31–#46) is additive. Every new setting defaults to the existing behavior:
  - `subagents.selection = off`;
  - `inference.tool_names = native`;
  - `subagents.remote_research = false`;
  - `classification.completed` gains only an optional key.
- No wire contract breaks: LA-WEB-PROVISIONING/1 stays exactly r4, and the API and SSE changes are additive.
- It follows the practice in effect: 0.4.0 for a structural change, then patch releases.

A minor bump (0.5.0) would be justified if the owner wants to signal the default-on behavior changes already listed under `[Unreleased] / Changed`. These are:
- workers share the lead's budget;
- generated role profiles are superseded;
- the depth limit is fixed.

That is the owner's call, and nothing in the repository forces either choice.

## Steps, once PR #30 and the stack are merged on `master`

1. Retarget each stacked PR to `master` **before** its base merges. GitHub closes a PR whose base branch is deleted on merge, as happened to #28.
2. Merge in order: #30, #31 … #46. Wait for `check` on `master` after each.
3. Make one commit, `chore: release v0.4.2`, on `master` with:
   - `Cargo.toml`: `[workspace.package] version = "0.4.2"`, and `Cargo.lock` with only the workspace members' versions changed. CI's "Cargo.lock is current" step checks that.
   - `frontend/package.json` and `frontend/package-lock.json`: `0.4.2`.
   - Optionally, `CHANGELOG.md`: promote `[Unreleased]` to `## [0.4.2] - <date>`, for readers only.
4. Wait for `check` on that commit, then push the tag `v0.4.2`. `release.yml` builds and publishes. Review the generated notes before announcing.

Every build, test and packaging step runs on GitHub Actions. Nothing is run locally.
