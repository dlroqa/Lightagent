## Preparation (branch `release/v0.5.0-dry-run`)

### Release gate (`.github/workflows/release.yml`)

- `workflow_dispatch` gains a typed boolean input `dry_run`, default `true`.
- A new `gate` job runs `scripts/release-gate.sh` with the event, ref type,
  ref name and `toJSON(inputs.dry_run)`. It prints `publish=true` only for:
  - a tag push whose tag is `v<workspace version>`, or
  - a manual run with `dry_run` exactly the boolean `false`, dispatched on
    that tag.

  A manual run with `dry_run=false` on a branch or another tag fails the
  gate, and nothing builds. Every other case prints `publish=false`: a dry
  run, an omitted input (default `true`; `null` would also stay dry), a
  string `"false"`, and any other event.
- `build` (unchanged steps and matrix) now waits for the gate.
- A new read-only `checksums` job writes `SHA256SUMS` over every package and
  uploads it as the `release-SHA256SUMS` artifact, for dry runs and releases
  alike.
- `publish` is the only job with `contents: write`. It runs only if
  `needs.gate.outputs.publish == 'true' && github.ref_type == 'tag'`, and
  attaches the `checksums` job's `SHA256SUMS` instead of computing its own.
  Its release action and settings (draft, generated notes) are unchanged.
- A tag push of `v<version>` behaves as before: build, checksum, draft.

### Gate tests (`scripts/test-release-gate.py`, job `release gate tests` in `check`)

- Decision cases through the real script: manual dry run (branch and tag),
  omitted input, non-boolean "false" values, `dry_run=false` on the tag, on a
  branch and on another tag, tag push matching and not, and non-release
  events (branch push, `pull_request`, `pull_request_target`, `schedule`,
  `workflow_run`, `release`, none).
- Workflow shape: triggers and input type/default, read-only default
  permissions, write permission only in `publish`, release- or tag-writing

  wiring, build and checksums ungated, and the three-platform matrix.

## How the candidate is run

GitHub's documentation: "This event will only trigger a workflow run if the
workflow file exists on the default branch", and a dispatch's `GITHUB_SHA` is
the "last commit on the `GITHUB_REF` branch or tag". `release.yml` already has
`workflow_dispatch` on `master`, so it can be dispatched on this branch
without merging, and the run uses the file at that commit: the gated
definition. The documentation does not state the last point outright, so the
run is checked as soon as it starts. Its job list must include `gate` and
`checksums`, which `master`'s file lacks. Otherwise it is cancelled during
the build, long before `master`'s `publish` could start.

Order, so a release-writing path is never reachable:
1. Push the branch and open a draft pull request. `check` runs the gate
   tests with the rest of CI.
2. Only once `release gate tests` passes: dispatch `release.yml` on
   `release/v0.5.0-dry-run` with `dry_run=true`. The ref is a branch, so even
   a broken gate cannot reach `publish` (its condition also requires a tag).
3. Inspect each job and step; confirm `publish` was skipped, and that no tag
   or release appeared.

## After merging

On the exact merge commit on `master`: `check`, `subagents` and
`jev evaluation` (push and pull-request triggers), then a `release.yml` dry
run on `master` with `dry_run=true`, covering all four platforms. Only then
create the tag `v0.5.0` on that commit. `[0.5.0]` is dated 2026-10-29. Tagging
on another date means changing the date in a new commit, and that commit
needs the same checks.
