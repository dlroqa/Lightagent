=== message
D5a-3: a run paused on its time budget continues over the API; steering

Time budget, as it was: an API run wraps up (one final tool-less turn,
then WallClockExceeded) and keeps nothing to resume. Only the terminal
paused, holding the loop's suspended state (the conversation with the tool
results the model has not read, and the turn and tool-call counts) in
memory, and `/continue` resumed that same execution. A new turn on the
session is not that: it starts a new execution from the saved transcript,
which does not hold unread tool results.

Now an API run may ask for the terminal's behavior:
- `POST /runs` takes `on_time_budget: "pause"` (default `wrap_up`, as
  before). Such a run pauses when its budget runs out with unread tool
  results: event `run.paused` {reason, elapsed_secs}, status
  `awaiting_continue`. It keeps its session lease and journal meanwhile.
- `POST /runs/{id}/continue` {mode: `extend` | `answer`} resumes the same
  execution: `extend` renews only the clock (turn and tool-call budgets
  still count) and carries on with tools; `answer` takes the final
  tool-less turn. 409 unless the run is paused. A revoked run takes none.
  A cancel ends a paused run (`run.cancelled`).
- The desktop contract gains `runs.continue`, refused during a profile
  switch like `runs.create`. The inventory gains its API row (not counted;
  it serves `slash.continue`, still not started until its UI is verified).
- The run factory trait gains `run_controlled` with a default that runs as
  before, so factories that cannot pause never do.

Steering: kept as it is, a FIFO queue held by the client (the terminal
process, the Web UI page) that sends each queued instruction as the
session's next turn once the session is free. Nothing is applied inside a
running turn; the queue does not survive its client; duplicate or
concurrent submissions are settled by the server's one-turn-per-session
admission. No backend queue is added (inventory `key.steer` updated).

OS locks: every `paths::lock_exclusive` lock (config, session writes, run
leases) is now an `ExclusiveLock` that unlocks before it closes, so none
stays held while a child is between fork and exec (row 20 fixed only the
run lease).

Evidence:
- crates/lightagent/tests/desktop_continue.rs (separate processes, all
  platforms): a paused run is `awaiting_continue` with one provider
  request; `extend` sends the next turn with the unread tool result and
  the tools; a second continue is refused; cancel while paused releases
  the session; a run that did not ask to pause wraps up.
- crates/lightagent/tests/desktop_interrupted.rs: a second runtime
  started while the first is mid-turn does not mark that turn
  Interrupted; it records it only after the first process is gone.
- run_lease.rs: a write lock dropped while a child is starting is free at
  once.
- desktop/e2e/runs.py `continue` (extend, answer, cancel, default
  wrap-up) and `steering` (busy refusal, two concurrent submissions with
  exactly one admitted, queued turns run in order) through the host.

/// An exclusive OS lock on a file, from [`lock_exclusive`]. Dropping it
/// unlocks, then closes. The lock belongs to the open file, which a child
/// that another thread is starting shares until its exec closes its copy, so
/// closing only this handle would keep the lock held until then; unlocking
/// releases it at once, whoever else still has the file open.
#[derive(Debug)]
pub struct ExclusiveLock {
    file: Option<std::fs::File>,
}

impl ExclusiveLock {
    /// The open file, still locked, without the unlock on drop: the lock then
    /// lasts until every copy of the file is closed (tests use this as a
    /// control).
    pub fn into_file(mut self) -> std::fs::File {
        self.file
            .take()
            .expect("a lock holds its file until it is dropped")
    }
}

impl Drop for ExclusiveLock {
    fn drop(&mut self) {
        if let Some(file) = &self.file {
            let _ = file.unlock();
        }
    }
}
