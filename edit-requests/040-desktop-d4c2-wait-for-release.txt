=== message
Wait for a session's release, not only its record, before the next prompt

Two older API tests posted a follow-up prompt as soon as the session file
showed the previous run's record. The recorder frees the session for its
next run just after that write, so in the gap between the two the
follow-up was refused (409 "session already has an active run"). On a
single-threaded test runtime the write and the release used to run back
to back, which hid the gap. With the record written on the blocking pool,
the test can see the file first (check 41367939822, linux-x64:
`session_history_is_packed_against_the_resolved_window`).

The API never promised that a visible record means a free session:
#98's `settled` helper and the profile-scoped regenerate test already wait
for the release, or retry on 409. These two tests now wait for the release
too. Nothing they assert changes.
